# 真机两层保护：Ctrl+C停车，空格＋Enter阻尼

运行完整真机任务的同一终端自动启用监听，不需要独立窗口。
正式`g1_pelvis_vln.py --execute`调用`run_g1_real.py`；后者创建独立监听进程读取原终端stdin，
模型、相机或iPlanner调用阻塞时，监听进程仍可工作。

| 输入 | 行为 |
|---|---|
| 空格 | 进入5秒待确认，不暂停任务、不发送阻尼、不写锁存 |
| 准备后Enter | 请求damping，回读FSM，并锁存导航 |
| 单独Enter、准备超时、其他普通键 | 不请求阻尼；取消/不进入准备 |
| Ctrl+C | 请求停车，结束导航并保存记录；随后保留保护待命 |
| 待命时再次Ctrl+C | 不退出保护，不恢复导航 |
| 待命时q再Enter | 明确关闭保护，退出程序；不切换机器人模式 |

Ctrl+C是零速度/StopMove，不是切换站立FSM，不调用HighStand、起身或恢复模式，
不能保证已经失衡的机器人站住。damping降低主动支撑，不是保持站立停车。
空格及Enter只对获得焦点的运行终端生效，不是系统全局快捷键。

## Ctrl+C之后为什么还能用

正式runner先完成原停车、本地记录、关闭DDS/相机/SLAM和远端会话结束，再通知独立
监听进入保护待命；runner本身暂不退出，所以同一个终端仍由程序占用，不出现shell提示符。
模型任务已经结束，不会重新开始导航。终端会显示：

```text
[DAMPING KEY] 导航资源已收尾，保护仍启用；空格+Enter=阻尼，q+Enter=退出保护。
[DAMPING KEY] 保护待命：空格→Enter仍可请求阻尼；q→Enter退出保护。
```

此时可以随时空格＋Enter阻尼；只有用户明确q＋Enter才关闭监听并恢复TTY。
正常任务结束及异常收尾也保留待命。SIGTERM为外部终止用途，不作为本功能的操作按键。
等待用户期间原`run_exit.json`和远端结束记录已经保存，不需要等q＋Enter才落盘。
启动器可能还在等待子进程退出，这是保护待命，不代表模型还在运行。

## 吊起机器人单独测试，不启动导航

先退出旧版测试（旧版Ctrl+C仍会退出），再重新运行新版；在内存中的旧进程不会因源码变化更新。
先停止其他导航/旋转程序。若上次已触发阻尼，由用户通过原有方式恢复运控802；
新版入口启动时会只读确认802后自动清除旧锁存，无需单独输入CLEAR。保持机器人吊起。

```bash
cd /home/yile/projects/unitree-g1-isaaclab-project
source /home/yile/projects/.venvs/unitree_g1/bin/activate
python scripts/isaacsim_lavira_g3_interface_g1/g1_damping_key.py \
  --network-interface enxf8e43bbea486
```

这个单独入口不启动模型、相机、导航或站立，不发送非零速度。
看到“已启用”后：

1. Ctrl+C：单独入口调用官方`SetVelocity(0,0,0)`（与StopMove同义），记录返回码与FSM，进入保护待命。
2. 再按Ctrl+C：仍待命，不退出。
3. 空格再在5秒内Enter：请求SetFsmId(1)，应显示已确认FSM=1。
4. q再Enter：退出保护，回到shell，不恢复站立。

如果已有本机阻尼锁存，单独入口的Ctrl+C不再发送零速度，以免在damping后覆盖命令；
它会明确记录skipped。此时仍可测试待命后的阻尼按键，但不能声称验证了停车RPC。
完整流程用原来的`g1_pelvis_vln.py --execute`命令即可，无需再启动第二个监听器。
本轮实现未代用户启动正式导航或发送真实模式切换。

## 锁存、记录与恢复

锁存：`~/.local/state/g1_safety/damping_<网卡名>.json`，运行中与退出时不会自动删除。
本项目`UnitreeG1DDSBackend`检测到锁存后，停止发送Move（含零速度），拒绝非零速度与HighStand，
cleanup不再发StopMove。新完整任务启动时只读确认FSM=802后自动处理旧锁存；
仍为1、未知模式或读取失败则保留并阻止任务，不发送恢复模式命令。旧进程看到锁存后，
删除文件也不会恢复，必须退出重启。

保留的手动清锁命令（正常使用新版入口已不需要；只删本机文件，不恢复机器人）：

```bash
python scripts/isaacsim_lavira_g3_interface_g1/g1_damping_key.py \
  --network-interface enxf8e43bbea486 --clear-latch
```

输入`CLEAR`再Enter确认；仅在所有导航/旋转程序停止后执行。

阻尼请求日志在`outputs/damping_key/terminal_*.json`，待命后触发记录
`standby_after_navigation=true`；单独测试的Ctrl+C记录为`standby_stop_*.json`。
FSM=1仅是模式回读，不是物理制动距离/响应时间测量。请求至多3轮，每次RPC超时1秒；
未确认时不误报成功，保留锁存并可再按空格＋Enter重试。

非TTY输入会明确提示未启用。其他电脑、遥控器、绕过本后端的SDK程序不受本机锁存控制；
同后端的旧旋转/单次跟随入口响应锁存但不自动启动监听。不能撤销已经在途的RPC，
网络/电脑/DDS故障、强制杀进程或关闭终端时不保证可触发，不替代原有紧急操作。
磁盘/权限导致锁存写入失败时仍请求阻尼，明确提示其他控制命令可能继续发送。

## 2026-10-22：新任务启动自动处理旧锁存

用户主动启动新的完整导航或单独按键测试时，自动检测旧锁存，不再逐次执行clear命令。

- 先退出旧任务/保护监听，手动通过原方式恢复机器人运控。
- 确认FSM=802后自动清除旧锁，打印“已确认FSM=802，自动清除上次阻尼锁存”。
- 该动作只调用GetFsmId，不调用HighStand、SetFsmId或恢复起身。
- 完整任务通过检查后才创建速度发送线程，随后继续原来的正式启动流程；
  原正式任务仍包含它原有的一次HighStand，与清锁检查不是同一操作。
- FSM=1或非802/通信异常时不自动清锁；完整任务阻止启动，单独按键测试保留锁存仍可请求阻尼。
- 新启动之前冻结旧锁存版本，查询期间新按下阻尼会改写请求版本，取消自动清锁；
  文件锁只用于短暂写入/删除，不在等待RPC时阻塞按键建立锁存。
- 仅启动时处理旧锁存，不在行走循环或Ctrl+C/阻尼之后自动删除；不会复活已锁存的旧进程。
- 正式任务另存damping_startup.json说明本次是否自动清锁；
  默认只读预检查不清锁，旧旋转/单次跟随入口未启用该自动处理。

自动清锁只是本机文件操作，不是机器人恢复姿态；目前仅接受已经实测过的802模式，
其他FSM需另行确认，不能任意把非1当作可导航。新版本需重新启动进程才生效。
332项离线测试通过，覆盖恢复802后清锁、阻尼/未知/读失败保留、启动中新增请求不被误删、
速度线程启动顺序及原有保护回归。实现时未清除当前实机锁存、未发送运动或模式切换。
